# 소액/테스트 주문 조건 설계 (HOLD 이후 1차)

## 0) 현재 상태와 목적
- 기준 문서: `Trading/실주문연결여부_최종판단.md`
- 현재 결론: **HOLD**
- 목적: 실주문 전면 오픈 전, **소액/제한 테스트 주문 허용 조건**과 **차단 조건**을 운영 가능한 수준으로 확정한다.
- 범위: 본 단계에서는 **실제 주문 실행 없음**. 허용/차단 로직과 제한값만 문서화한다.

---

## 1) 왜 아직 HOLD 인가
아래 중 하나라도 충족되지 않으면 HOLD를 유지한다.
1. post_close 확정 신호 기반의 일관된 pass 누적 부족
2. 상태/로그 저장 안정성 검증 부족 (누락/지연/실패 케이스)
3. gate fail 또는 recent change 과도 상태가 반복
4. 우선순위가 높아도 근거가 약한 케이스 필터링 불충분
5. 급등 노이즈성 움직임 차단 기준의 자동 판별 신뢰도 미달

---

## 2) 테스트 주문 허용 범위 (정량 제한)
보수 운영을 위해 아래 제한을 동시에 적용한다.

### 2-1. 주문 금액/수량 제한
- **최소 주문 금액**: 100,000 KRW
- **최소 주문 수량**: 1주
- **1회 최대 테스트 금액**: 300,000 KRW
- **종목별 1일 최대 테스트 금액**: 300,000 KRW
- **전체 1일 최대 테스트 금액**: 600,000 KRW

### 2-2. 횟수/보유 수 제한
- **1일 최대 테스트 주문 횟수**: 2회
- **동시 보유 가능 종목 수**: 최대 2개
- 동일 종목 재진입은 당일 1회까지만 허용

### 2-3. 주문 방식 제한
- 시장가 추격 금지, 지정가 기반만 허용
- 시가 급등 구간(갭 상승 과도) 신규 진입 금지
- 장중 신규 신호 단독 진입 금지 (예외는 3-3 참고)

---

## 3) 테스트 대상 제한

### 3-1. 종목군
- 대표주 우선
- 일평균 거래대금/거래량이 충분한 종목만 허용
- 동시성/체결 안정성 낮은 종목 제외

### 3-2. 제외 조건
아래 조건은 즉시 제외한다.
- 산업 고단계(4~5단계)
- `leader_alignment = broken`
- `foreign_flow = only_strong` 단독 케이스

### 3-3. phase 조건
- **intraday 단독**: 기본 금지
- **post_close confirmed**: 우선 허용 검토
- `final_decision = pass` 인 경우만 후보 편입
- `review`, `hold`, `block`: 주문 금지

---

## 4) 테스트 주문 차단 조건 (필수)
아래 중 하나라도 참이면 테스트 주문도 금지.

1. 필수 필드 누락
2. gate fail
3. 로그/상태 저장 실패
4. recent change 과도
5. 우선순위는 높지만 근거 약함
6. 급등 노이즈성 움직임 탐지

추가 운영 규칙:
- 차단 사유 발생 시 `blocked_reason`을 단일 문자열이 아닌 배열로 남긴다.
- 차단 발생 건은 당일 재평가하되 자동 해제 금지(수동 확인 후 해제).

---

## 5) 테스트 주문 산출 구조 (표준)
아래 구조를 테스트 주문 판단의 공통 포맷으로 사용한다.

```json
{
  "as_of": "2026-04-24",
  "ticker": "005930",
  "test_order_allowed": false,
  "allowed_reason": [],
  "blocked_reason": [
    "phase_not_post_close_confirmed",
    "final_decision_not_pass"
  ],
  "max_order_amount": 300000,
  "max_order_quantity": 1,
  "daily_limit": {
    "max_orders_per_day": 2,
    "max_total_amount_per_day": 600000,
    "max_amount_per_ticker_per_day": 300000,
    "max_concurrent_positions": 2
  },
  "eligible_tickers": [
    "005930",
    "000660"
  ]
}
```

필드 정의:
- `test_order_allowed`: 최종 허용 여부
- `allowed_reason`: 허용 근거 목록 (`post_close_confirmed`, `final_decision_pass` 등)
- `blocked_reason`: 차단 근거 목록
- `max_order_amount`: 1회 허용 최대 금액
- `max_order_quantity`: 1회 허용 최대 수량
- `daily_limit`: 일일 한도 객체
- `eligible_tickers`: 당일 허용 가능한 종목 리스트

---

## 6) 운영 판단 플로우
1. 필수 필드/저장 상태 검증
2. gate 통과 여부 확인
3. phase 확인 (`post_close confirmed` 우선)
4. `final_decision = pass` 확인
5. 종목 제한 조건/제외 조건 확인
6. 일일 금액/횟수/동시보유 한도 확인
7. 최종 `test_order_allowed` 산출

어느 단계에서든 fail이면 즉시 차단한다.

---

## 7) 소액 테스트 전환 조건 (HOLD → TEST)
아래를 모두 만족하면 소액 테스트 주문 단계로 전환 검토.

- 최근 영업일 기준 post_close confirmed + pass 누적이 안정적
- 로그/상태 저장 실패율이 운영 허용치 이내
- 차단 조건 자동 탐지 정확도가 수동 검토와 유사
- dry-run 결과에서 과도한 노이즈 진입 케이스가 억제됨

---

## 8) 소액 테스트 후, 실주문 확대로 가기 위한 확인 항목
1. 체결 품질: 슬리피지/미체결/지연 수준
2. 필터 품질: 차단해야 할 케이스 차단 성공률
3. 신호 품질: post_close 기반 pass의 일관성
4. 안정성: 상태 저장/로그/복구 동작
5. 리스크: 일 손실 제한 준수 여부

위 항목이 기준치를 만족하기 전까지는 전면 실주문 확대 금지.

---

## 9) 다음 행동
1. 본 문서 기준으로 dry-run 출력 스키마(`test_order_allowed` 등) 반영
2. 1주 단위로 테스트 허용/차단 로그 리뷰
3. 필요 시 제한값(금액/횟수) 추가 축소
4. 테스트 주문 실행 여부 재판단 후, 단계적 확대 여부 결정
