# 주문전 최종판단 레이어 설계

## 1) 목적/범위
- 목적: 장중 임시 신호 + 장후 확정 신호를 **주문 직전 관점**에서 최종 해석한다.
- 범위: 자동주문 실행 로직 이전의 판단 계층만 설계한다.
- 비범위: 주문 전송 API 호출, 체결 후 포지션 관리 자동화.

---

## 2) 최종 판단 상태 체계

| 상태 | 의미 | 주문 가능 여부 | 운영 원칙 |
|---|---|---|---|
| `pass` | 주문 검토 가능 | 가능(검토 후) | 차단 규칙 미해당 + 통과 조건 충족 |
| `hold` | 보류 | 불가(재평가 필요) | 정보 부족/근거 약함/타이밍 불명확 |
| `block` | 차단 | 불가(당일 제외) | 리스크/충돌 조건 명시적 위배 |
| `review` | 수동 확인 필요 | 수동 승인 전 불가 | 자동 규칙 충돌/예외적 고점검 필요 |

상태 우선순위(강한 것 우선):
1. `block`
2. `review`
3. `hold`
4. `pass`

> 즉, 통과 조건이 좋아도 차단 조건이 하나라도 맞으면 `block`이 우선된다.

## 3) 판단 입력 정의

최종 판단 함수 입력(필수/권장):

```json
{
  "market_phase": "intraday|post_close",
  "final_classification": "실행검토|매수대기|후보신호|관망",
  "intraday_classification": "temporary_signal_type",
  "total_score": 0,
  "intraday_execution_score": 0,
  "execution_priority": 0,
  "priority_reason": "문장",
  "industry_stage": 1,
  "leader_follower_alignment": "aligned|mixed|broken",
  "recent_change_summary": "문장",
  "foreign_flow_signal": "none|foreign_only_strong|broad_participation",
  "intraday_noise_flag": true,
  "evidence_strength": "strong|medium|weak",
  "required_fields_complete": true,
  "phase_consistency": true,
  "decision_timestamp": "2026-04-23T00:00:00Z"
}
```

필수 필드:
- `final_classification`
- `intraday_classification`
- `total_score`
- `intraday_execution_score`
- `execution_priority`
- `industry_stage`
- `leader_follower_alignment`
- `recent_change_summary`
- `required_fields_complete`
- `phase_consistency`

권장 필드:
- `priority_reason`
- `foreign_flow_signal`
- `intraday_noise_flag`
- `evidence_strength`

## 4) 규칙 설계

### 4-1. 차단(`block`) 규칙
아래 중 하나라도 참이면 `block`:

1. `industry_stage >= 4` 이고 과열/고점 경계 해제 근거 없음
2. `foreign_flow_signal == foreign_only_strong` (외국인 단독 강세)
3. `leader_follower_alignment == broken`
4. `intraday_noise_flag == true` (급등/거래대금 급변 노이즈)
5. `recent_change_summary`가 급변을 말하지만 `evidence_strength == weak`
6. `required_fields_complete == false`
7. `phase_consistency == false` (intraday/post_close 해석 충돌)

차단 사유는 `decision_flags`에 누적 기록.

### 4-2. 보류(`hold`) 규칙
차단은 아니지만 아래 중 하나라도 참이면 `hold`:

1. `final_classification`이 `후보신호` 수준이고 장후 확정 근거가 약함
2. `intraday_execution_score`는 높지만 `total_score`가 기준 미달
3. `execution_priority` 중간권(예: 40~69)으로 확신 부족
4. `leader_follower_alignment == mixed`
5. `priority_reason`/`recent_change_summary` 문장 품질 저하(사유 불명확)

### 4-3. 수동확인(`review`) 규칙
자동 판정 충돌이 있으면 `review`:

1. `pass` 조건과 `hold` 조건이 동시에 강하게 성립
2. 점수는 높지만(상위 10~20%) 산업/수급 해석이 엇갈림
3. 규칙 엔진 간 상충(예: phase 판단 모듈 불일치)

### 4-4. 통과(`pass`) 규칙
차단/보류/리뷰에 해당하지 않고 아래 전부 충족 시 `pass`:

1. 장후 `final_classification` 우호(실행검토/매수대기 상위)
2. `intraday_execution_score` 우호(기준 이상)
3. `execution_priority` 상위권
4. `priority_reason` + `recent_change_summary` 사유 명확
5. `leader_follower_alignment == aligned`
6. 필수 필드 완전 + phase 정합성 정상

---

## 5) 점수/임계치 기본안(초기값)

- `total_score_pass_min = 70`
- `intraday_execution_score_pass_min = 65`
- `execution_priority_pass_min = 70`
- `execution_priority_hold_band = 40..69`
- `review_conflict_band = total_score>=75 AND intraday_execution_score>=75 AND alignment!=aligned`

> 초기값은 보수적으로 시작하고, 2주 단위 샘플 리플레이로 보정한다.

## 6) 최종 산출 구조(Output Schema)

```json
{
  "final_decision": "pass|hold|block|review",
  "decision_reason": "사람이 읽기 쉬운 1~2문장",
  "decision_flags": [
    "INDUSTRY_STAGE_HIGH",
    "LEADER_ALIGNMENT_BROKEN"
  ],
  "required_next_action": "주문검토|관찰지속|당일제외|수동검토",
  "decision_timestamp": "2026-04-23T00:00:00Z",
  "input_snapshot": {
    "final_classification": "실행검토",
    "intraday_classification": "temporary_breakout",
    "total_score": 78,
    "intraday_execution_score": 74,
    "execution_priority": 82,
    "industry_stage": 2,
    "leader_follower_alignment": "aligned"
  }
}
```

`required_next_action` 매핑:
- `pass` → `주문검토`
- `hold` → `관찰지속`
- `block` → `당일제외`
- `review` → `수동검토`

---

## 7) 판정 순서(권장 알고리즘)

1. 입력 필수값 검증
2. phase 정합성 검증
3. 차단 규칙 평가 (`any-match`)
4. 보류 규칙 평가
5. 리뷰 규칙 평가
6. 통과 규칙 평가 (`all-match`)
7. 기본값 fallback = `hold`

의사코드:

```text
if !required_fields_complete or !phase_consistency:
  return block
if any(block_rules):
  return block
if any(review_rules):
  return review
if any(hold_rules):
  return hold
if all(pass_rules):
  return pass
return hold
```

## 8) 샘플 시나리오 검증

### 시나리오 A: 통과(pass)
- 입력: final=실행검토, total=79, intraday_exec=77, priority=85, stage=2, alignment=aligned, evidence=strong
- 판정: `pass`
- 이유: 장후/장중 모두 우호, 정렬 양호, 필수값 완전

### 시나리오 B: 보류(hold)
- 입력: final=매수대기, total=68, intraday_exec=72, priority=58, stage=3, alignment=mixed, evidence=medium
- 판정: `hold`
- 이유: 장중 강도는 있으나 우선순위 중간권 + 정렬 혼합

### 시나리오 C: 차단(block)
- 입력: final=실행검토, total=82, intraday_exec=80, priority=88, stage=4, alignment=aligned, foreign_only_strong
- 판정: `block`
- 이유: 고단계 + 외국인 단독 강세 차단 규칙 우선

### 시나리오 D: 수동확인(review)
- 입력: final=실행검토, total=84, intraday_exec=81, priority=79, stage=3, alignment=mixed, evidence=strong
- 판정: `review`
- 이유: 점수 상위지만 정렬 불완전으로 자동 통과/보류 충돌

검증 체크:
- 상태 분리 명확성: pass/hold/block/review 상호 배타
- 신호 혼용 방지: intraday는 보조, post_close는 기준
- 보수성: block 조건 1개라도 일치 시 즉시 제외
- 설명가능성: `decision_reason`은 1~2문장으로 사람이 즉시 이해 가능

## 9) 운영 메모(다음 단계 연결)
- 자동주문 연결 전, 본 레이어를 `dry-run`으로 최소 2주 재생 검증
- `block`/`review` 비율이 과다하면 임계치 조정
- 주문 시뮬레이션에서 `pass`만 실행 후보로 전달
