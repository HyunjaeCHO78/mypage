# Trading/실매매프로젝트_전달포맷정리

## 1) 목적
- intraday_priority_ranking 1차 고도화 결과를 실매매 프로젝트가 바로 읽을 수 있는 전달 포맷으로 고정한다.
- 장중 임시 신호(`intraday`)와 장후 확정 신호(`post_close`)를 구조/파일 단위로 분리한다.
- 자동주문 로직은 붙이지 않고, 전달 포맷과 해석 기준만 먼저 확정한다.

## 2) 신호 분리 원칙 (고정)
- 장중 파일: `Trading/INTRADAY_SIGNAL_BRIDGE.json`
  - `market_phase=intraday`
  - `signal_type=temporary`
- 장후 파일: `Trading/INTEGRATED_SIGNAL_BOARD.json`
  - `market_phase=post_close`
  - 기존 확정 신호 구조 유지
- 실매매 프로젝트는 `market_phase`와 파일 경로를 동시에 확인해서 혼용을 방지한다.

## 3) 전달 포맷 정의

### 3-1. 공통 필드
- `date`: 신호 기준 일자
- `market_phase`: `intraday` 또는 `post_close`
- `signals`: 종목 신호 배열
- `ticker`, `name`, `industry`
- `execution_priority`

### 3-2. 장중 전용 필드 (`INTRADAY_SIGNAL_BRIDGE.json`)
- `signal_type`: `temporary` 고정
- `version`: 전달 포맷 버전
- `generated_at`: 파일 생성 UTC 시각
- `role`: 대표주/후발주
- `intraday_execution_score`: 장중 실행 점수
- `intraday_classification`: 장중 분류
- `priority_reason`: 우선순위 산정 사유
- `last_updated`: 종목 신호 최신 갱신 시각
- `recent_change_summary`: 최근 변화 요약

### 3-3. 장후 전용 필드 (`INTEGRATED_SIGNAL_BOARD.json`)
- `generated_at`: 파일 생성 UTC 시각
- `scores.total`: 최종 총점
- `final_classification`: 장후 확정 분류
- `bridge_ready`: 실매매 브리지 전달 준비 여부
- `next_action`: 다음 거래일 확인 행동
- `last_updated`: 종목 신호 최신 갱신 시각
- (기존 `raw_classification`, `adjustments`, `evidence_summary` 유지)

## 4) 실매매 프로젝트 해석 기준

### 4-1. 매수대기/실행검토 판독 기준
- 장중 판독(참고용):
  - `intraday_classification`
  - `intraday_execution_score`
  - `execution_priority`
  - `priority_reason`
- 장후 판독(확정용):
  - `final_classification`
  - `scores.total`
  - `bridge_ready`
  - `next_action`

### 4-2. 신호 해석 범위
- 장중 신호는 임시 신호이므로 "실행검토"여도 자동주문 트리거로 사용하지 않는다.
- 장후 신호만 확정 분류로 사용하며, 기존 `INTEGRATED_SIGNAL_BOARD.json`을 단일 기준으로 삼는다.
- 우선순위 충돌 시 `post_close` 기준을 우선하고, 장중 값은 장중 모니터링 설명값으로만 사용한다.

### 4-3. 실매매 프로젝트 최소 읽기 키(권장 우선순위)
- 공통 우선순위:
  1) `market_phase` 확인
  2) `ticker`
  3) `classification`
  4) `score`
  5) `priority`
  6) `reason`
  7) `generated_at` / `last_updated`
- 장중(`intraday`) 매핑:
  - `classification` ← `intraday_classification`
  - `score` ← `intraday_execution_score`
  - `priority` ← `execution_priority`
  - `reason` ← `priority_reason`
- 장후(`post_close`) 매핑:
  - `classification` ← `final_classification`
  - `score` ← `scores.total`
  - `priority` ← `execution_priority`
  - `reason` ← `next_action`

## 5) 샘플 출력 위치
- 장중 샘플(3개): `Trading/examples/intraday_signal_bridge.sample.json`
- 장후 샘플(2개): `Trading/examples/post_close_signal_bridge.sample.json`

## 6) 검증 항목
- 장중 파일에 `priority/classification/score/reason`이 모두 존재하는지 확인
- 장중 파일이 `market_phase=intraday`, `signal_type=temporary`인지 확인
- 장후 파일이 `market_phase=post_close`이고 `final_classification/scores.total/bridge_ready/next_action`을 유지하는지 확인
- `generated_at`/`last_updated`가 장중/장후 모두 존재하는지 확인
- 숫자 필드(`score`, `priority`)와 문자열 필드(`ticker`, `classification`, `reason`) 타입 유지 확인
- 기존 `INTEGRATED_SIGNAL_BOARD.json`과 장중 파일의 경로/phase가 분리되어 충돌하지 않는지 확인

## 7) 읽기/매핑 검증 스크립트
- 전달 포맷 검증(필수 필드 + 타입 + phase 충돌):
  - `python Trading/validate_signal_delivery_formats.py`
- 실매매 읽기 기준 검증(최소 파싱 + 내부 매핑 + 샘플 개수):
  - `python Trading/validate_signal_read_mapping.py`
