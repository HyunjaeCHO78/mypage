# 단일 축소안 테스트 주문 체크리스트 확정

## 0) 문서 목적 / 범위
- 기준 시점: **2026-04-25 (UTC)**
- 목적: `1종목 / 1일 1회 / 100,000 KRW` 단일 축소안 테스트 주문을 **실행 직전 표준 절차**로 고정
- 범위: 이번 단계는 **실제 주문 실행 없음**, 체크리스트/중단 기준/사후 보고 체계만 확정
- 기본 운영 상태: **`hold_test` 유지**
- 예외 허용 상태: 아래 모든 조건 충족 + 수동 승인 완료 시에만 **조건부 1회 허용 검토**

---

## 1) 단일 축소안 최종 고정값

### 1-1. 실행 한도 (변경 금지)
- 종목 수: **1종목만**
- 일일 주문 횟수: **1일 1회만**
- 주문 금액: **100,000 KRW (고정)**
- 주문 방식: **지정가만 허용**
- 동시 보유: **최대 1개**

### 1-2. 필수 게이트 조건 (전부 충족 필요)
1. `market_phase=post_close`
2. `source_signal_type=post_close_confirmed`
3. `final_decision=pass`
4. `blocked_reason=[]` (빈 배열)
5. `status=pass` (pre-live gate)
6. `state_write_ok=true`, `log_write_ok=true`
7. `human_approval=true` (승인자/시각/사유 기록)

하나라도 불충족이면 **주문 금지**.

---

## 2) 실행 전 체크리스트 (Pre-Trade)
아래 12개 항목을 모두 `PASS` 해야만 주문 요청 단계로 이동한다.

### 2-1. 신호/의사결정 검증
1. `post_close_confirmed` 신호 여부 확인
2. `final_decision=pass` 여부 확인
3. `blocked_reason` 빈 배열 확인
4. 당일 재계산 시 동일 결론 유지 확인(값 변형 없음)

### 2-2. 한도/리스크 검증
5. 대상 종목 1개만 선택되었는지 확인
6. 당일 주문 횟수 0회 확인(이미 1회면 금지)
7. 주문 금액이 정확히 100,000 KRW인지 확인
8. 동시 보유 종목 수가 0 또는 허용 범위(최대 1)인지 확인

### 2-3. 시스템/기록 검증
9. pre-live gate `status=pass` 최신값 확인
10. `state_write_ok=true`, `log_write_ok=true` 확인
11. 주문/체결 로그 경로 쓰기 가능 확인
12. 승인자 수동 서명(전자/문서) 완료 확인

### 2-4. 실행 전 선언 문구 (필수)
- "체크리스트 12/12 PASS, 단일 축소안(1종목/1회/10만원/지정가) 조건 충족, 수동 승인 완료"를 기록 후 진행.

---

## 3) 실행 중 확인 항목 (In-Trade)
주문 요청부터 체결 확인까지 아래를 순서대로 점검한다.

1. 주문 요청 payload 재확인
   - ticker 1개
   - amount=100000
   - order_type=limit
2. 주문 ID 생성/수신 확인
3. 중복 주문 발생 여부 실시간 확인 (`duplicate_order=false`)
4. 체결 가격이 허용 범위 내인지 확인 (비정상 괴리 없음)
5. 체결 지연 임계시간 초과 여부 확인
6. 주문/체결/상태 로그가 모두 기록되는지 확인
7. 이상 이벤트 발생 시 즉시 `test_order_enabled=false` 전환

실행 중 원칙:
- **승인 조건이 깨지는 순간 즉시 중단**
- **당일 재시도 금지**

---

## 4) 실행 후 리포트 항목 (Post-Trade)
주문 종료 후 당일 반드시 아래 보고를 남긴다.

### 4-1. 필수 리포트 필드
1. `decision_snapshot`
   - phase, signal_type, final_decision, blocked_reason
2. `limit_snapshot`
   - orders_today, amount_today, concurrent_positions, applied_limit_profile
3. `execution_result`
   - requested_price, filled_price, fill_status, latency_ms
4. `system_health`
   - gate_status, state_write_ok, log_write_ok
5. `anomaly_detected`
   - true/false + 상세 사유
6. `human_approval_record`
   - 승인자, 승인시각, 승인근거
7. `final_label`
   - `reapprove_candidate` 또는 `rehold_candidate` 또는 `reblock`

### 4-2. 사후 결론 기록
- 무이상: `reapprove_candidate`
- 경미 이상(원인 분석 필요): `rehold_candidate`
- 중대 이상/규칙 위반: `reblock`

---

## 5) 즉시 중단 기준 (Kill Switch)
아래 중 하나라도 발생하면 즉시 중단한다.

1. `phase_not_post_close_confirmed`
2. `final_decision_not_pass`
3. `blocked_reason` 신규 발생
4. 승인 누락 상태에서 주문 시도 감지
5. 제한값 위반 또는 위반 시도
   - 1일 1회 위반
   - 10만원 초과 시도
   - 동시보유 1 초과 시도
6. 비정상 체결
   - 중복 체결
   - 허용범위 밖 가격
   - 과도한 체결 지연
7. 저장 실패
   - state write fail
   - log write fail

중단 후 강제 조치:
- `test_order_enabled=false`
- 당일 추가 주문 전면 금지
- 원인/재발방지 문서화 전 재개 금지

---

## 6) 재승인 / 재보류 판단 흐름 (T+0 종료 후)

### 6-1. 판단 트리
1. **중단 기준 발생 여부 확인**
   - Yes → `reblock`
   - No → 2단계
2. **리포트 필수 필드 완전성 확인**
   - 미완료 → `rehold_candidate`
   - 완료 → 3단계
3. **체결/로그/상태 무이상 여부 확인**
   - 이상 있음 → `rehold_candidate`
   - 무이상 → `reapprove_candidate`

### 6-2. 다음 행동 규칙
- `reapprove_candidate`:
  - 다음 영업일 동일 단일 축소안으로 1회 재검토 가능
- `rehold_candidate`:
  - 원인 보정 전 실행 금지, HOLD 유지
- `reblock`:
  - 차단 상태 유지, 운영 레벨 재심의 전 테스트 주문 금지

---

## 7) 최종 운영 선언
1. **체크리스트 미충족 시 주문하지 않는다.**
2. **수동 승인 없이는 진행하지 않는다.**
3. **`post_close_confirmed + final_decision=pass + 차단 플래그 없음`은 절대 필수다.**
4. **주문 후 반드시 리포트 작성 및 재승인/재보류 판단까지 완료한다.**
