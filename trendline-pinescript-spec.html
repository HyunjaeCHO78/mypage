HJ 추세선 전략 PineScript 설계 규칙 v1

이 문서는 HJ 추세선 전략을 TradingView PineScript 기반의 시각화/알림/백테스트 구조로 옮기기 위한 설계 명세서이다. 실제 코드를 바로 쓰기 전에, 추세선 전략의 규칙을 코드 가능한 것과 코드 불가능/주관적 요소로 분해하는 목적이다.

문서의 역할

실전 매매 지침서가 아니라, 개발 전에 규칙 정의를 확정하기 위한 사양 문서다.

주요 산출물

Pivot, 추세선, breakout, retest, safety line, risk 규칙을 코드 설계 언어로 번역한다.

핵심 원칙

완전 자동화보다 먼저 반자동 구조화와 경고/후보 선별 도구를 만드는 방향을 우선한다.

설계 목표

추세선 전략을 코딩 전에 구조화하여, 구현 범위와 재량 판단의 경계를 명확히 한다.

Specification Scope
구조화

추세선 전략을 코드 관점에서 구조화하고 데이터 입력, 판단 규칙, 출력 이벤트로 나눈다.

주관성 최소화

재량 요소를 인정하되 최대한 수치화 가능한 룰로 변환해 개발 범위를 좁힌다.

백테스트 가능성 구분

백테스트 가능한 규칙과 불가능한 규칙을 분리해 전략 결과 해석 오류를 줄인다.

재사용성

시각화, 경고(alert), 조건 검색, 전략 테스트에 재사용 가능하도록 규칙을 정리한다.

단계적 구현

지표 → 알림 → 점수화 → strategy 순서로 확대 가능한 설계 골격을 만든다.

검증 준비

실제 PineScript 작성 전에 반드시 확정해야 할 입력 변수와 예외 케이스를 선제적으로 드러낸다.

Discretion Boundaries

“유효한 추세선” 정의의 주관성

같은 pivot 조합이라도 사람이 보는 의미 있는 추세선과 기계가 뽑는 선은 다를 수 있다.

fan 구조 선택 문제

동일한 구간에서 여러 팬형 추세선이 생성될 수 있어 어떤 선을 action line으로 볼지 자동 선택이 어렵다.

가장 의미 있는 추세선 선택

touch 수, 각도, 기간, 반응 강도 중 무엇을 우선할지 규칙이 필요하지만 절대적 기준이 없다.

횡보장 / 잡음 구간 제거

피벗은 많지만 방향성이 없는 구간을 필터링하지 않으면 의미 없는 선이 과도하게 발생한다.

수평 지지저항 해석

추세선 자체보다 수평 레벨과 결합될 때 의미가 커지지만, 어떤 레벨이 핵심인지 판별이 어렵다.

fakeout의 완전 제거 불가

종가 기준 breakout을 써도 모든 함정 이탈을 제거할 수 없으며, 이는 결과 해석 시 전제 조건이다.

세션 맥락 / 뉴스 / discretionary filter

세션 변동성, 이벤트 리스크, 뉴스 해석은 PineScript로 정밀 구현하기 어려운 재량 필터다.

Pivot 규칙 제안

추세선 전략의 기초 데이터는 pivot 정의에서 결정된다.

Foundation Rules

기본 정의

  • pivot high / pivot low는 좌우 N봉 기준으로 정의한다.
  • 예: left = N, right = N 형태의 대칭 pivot 규칙을 기본값으로 고려한다.
  • PineScript 구현 시 pivot 확정은 right bars 이후에 확정된다는 점을 문서화한다.

빠른 / 느린 모드

  • 빠른 pivot: 작은 N으로 민감도는 높지만 노이즈 증가.
  • 느린 pivot: 큰 N으로 신뢰도는 높지만 시그널 지연 증가.
  • 전략 초기 버전에서 모드를 분리해 비교 가능하도록 설계한다.

노이즈 억제 필터

  • 연속 pivot 간 최소 봉 수(min bars between pivots) 필터를 둘 수 있다.
  • 최소 변동폭(min swing distance) 또는 % 변동폭 필터를 함께 검토한다.
  • ATR 배수 기반 필터를 추가하면 종목별 변동성 차이를 일부 보정할 수 있다.

설계 메모

  • Pivot 규칙은 이후 3터치, 추세선 후보 생성, risk distance 계산의 공통 기반이 된다.
  • 따라서 pivot length는 가장 먼저 백테스트 파라미터화해야 할 핵심 입력 변수다.

3터치 인정 규칙 제안

“라인이 살아 있다”는 판단을 기계적으로 근사하기 위한 최소 조건이다.

Touch Validation
  • 한 추세선 위/아래로 최소 3회 가격 반응이 있어야 인정하는 구조를 기본안으로 둔다.
  • 실제 데이터에는 완벽한 일치가 드물기 때문에 허용 오차(tolerance) 설정이 필요하다.
  • tolerance는 % 기준, tick 기준, ATR 비율 기준 중 하나로 입력값화할 수 있다.
  • wick 기준 / body 기준 / 혼합 기준을 모드로 나눠 비교 가능하게 설계한다.
  • 너무 촘촘한 3터치는 의미 없는 잡음일 수 있으므로 touch 간 최소 봉 간격을 둔다.
  • 의미 있는 추세선만 남기기 위해 전체 데이터 기간 필터(예: 최소 유지 봉 수)를 둔다.

검토 포인트

  • touch는 pivot 기준으로 셀지, 일반 캔들 접촉까지 포함할지 결정해야 한다.
  • 정확도보다 실용성을 위해 “근사치 터치”를 허용하는 편이 알림용 지표에 적합하다.
  • 반대로 strategy 버전에서는 지나친 유연성이 과최적화로 이어질 수 있으므로 범위를 제한해야 한다.

breakout 규칙 제안

이탈 신호는 가장 자주 오해되는 영역이므로 candle close 기준을 우선 정의한다.

Breakout Logic

핵심 규칙

  • wick 돌파만으로는 breakout으로 인정하지 않는다.
  • 종가 기준 breakout을 우선하며, 가능하면 body close beyond line 조건을 기본값으로 둔다.
  • 종가가 추세선 바깥에서 마감한 뒤에만 확정 이벤트를 발생시킨다.
  • breakout 이후 허용 봉 수 안에서만 retest를 인정하도록 제한한다.

retest 설계

  • retest는 breakout 후 N봉 이내 재접촉 + 반대 방향 재이탈 조건으로 정의할 수 있다.
  • retest 허용 오차는 line tolerance와 동일하게 쓰거나 별도 변수로 분리할 수 있다.
  • retest를 엔트리 후보로만 사용할지, breakout 확정 보강 신호로 사용할지 문서에서 구분한다.

safety line 설계 규칙

action line만으로는 방어 구조가 부족하므로 반대편 구조 추적 규칙이 필요하다.

Risk Control Layer
  • action line 반대편 구조를 safety line 후보로 사용한다.
  • 코드상 safety line은 독립 line 객체 또는 최근 pivot 기반 보조 라인 배열로 추적할 수 있다.
  • 포지션 방향에 따라 safety line을 stop 기준선 또는 경보 기준선으로 재사용할 수 있다.
  • 더 가파른 새 추세선이 생길 때 trailing 업데이트를 할지 여부를 별도 옵션으로 둔다.

구현 해석

  • 초기 버전은 trailing stop 성격의 시각화 라인으로 구현하는 것이 가장 단순하다.
  • strategy 버전에서는 safety line breach를 청산 조건으로 연결하는 실험이 가능하다.
  • 다만 safety line 자체의 선택 기준도 주관성이 있으므로 완전 자동 규칙이라고 간주하지 않는다.

risk / sizing 관련 문서화

PineScript는 리스크 계산을 보조할 수 있지만 브로커 수준의 실제 집행 로직과는 구분해야 한다.

Sizing Constraints
  • PineScript 전략에서 실제 포지션 크기 계산에는 한계가 있으며, 브로커별 체결 조건까지 완전 반영하기 어렵다.
  • 계좌 기반 1% 리스크 계산은 입력값 기반 시뮬레이션 형태로만 구현하는 것이 현실적이다.
  • 따라서 sizing은 “정확한 실행 엔진”보다 “의사결정 보조값”으로 보는 것이 적절하다.

가능한 시각화

  • risk distance 자체는 시각화 가능하다.
  • 저위험/고위험은 risk distance 기준으로 색상 표시가 가능하다.
  • 리스크 임계값을 넘는 셋업에 경고 배지를 부여해 후보 선별 도구로 사용할 수 있다.

A+ 점수화 가능 항목 / 불가능 항목

점수화는 전체 전략을 대체하는 것이 아니라, 사람의 검토 순서를 줄이는 데 목적이 있다.

Semi-Auto Scoring

A. 코드화 가능

  • 3터치
  • 종가 breakout
  • retest 여부
  • 상위봉 방향 정렬(단순화 버전)

  • 정말 의미 있는 수평 레벨 판별
  • discretionary pass 판단

구현 우선순위

처음부터 strategy를 만들기보다 시각화와 검증 가능한 층위를 먼저 쌓아야 한다.

최종 결론

  • 이 전략은 완전 자동화보다 “반자동 구조화”가 먼저다.

문서 활용 방식

이 페이지는 운영 기준서, 체크리스트, 저널 템플릿을 개발 관점으로 번역한 연결 문서다. 즉, 기존 문서가 실전 운영 규율을 설명한다면 본 문서는 PineScript 설계와 백테스트 준비를 위한 규칙 합의서 역할을 한다.

운영 기준서로 이동 체크리스트로 이동 저널 템플릿으로 이동 맨 위로
